## 0. Разведка (факты, установлены до кода)

- (а) Блок = запись `store.groups[]`: сейчас только `{name}`; порядок массива —
  порядок блоков; имена уникальны. Пункт ссылается на блок ИМЕНЕМ (`item.group`,
  строка). Пункт: `{id, name, value, unit, type: daily|weekly|param, area: min|habit,
  goal, note, group, removedAt, addedAt, schedule? (только daily), at, normPerWeek
  (только daily habit), pkind/pvalue/pstep (param), raiseAfter, raiseAfterWeek,
  lowerAfterWeek, history, formula, ladder, ladderLog}`.
- (б) Маска у пункта ЕСТЬ и хранится ОТРЕЗКАМИ: `item.schedule = [{from, mask}]`
  (задача 29/B, `scheduleOn`, `setSchedule`, `normSchedule`). Стоп-условие 1 не
  срабатывает. Маска пункта становится ПЕРЕОПРЕДЕЛЕНИЕМ, её история сохраняется.
- (в) «Сегодня»: `renderToday` → `dueDaily('min', t)` → `dueNow`; «N из M» — там же
  и в точечном `updateDayline`; «день закрыт» — `minDayClosed` → `minDayMarks` →
  `minDayItems(dayKey)` → `dueOn`; зачёт — `dayScore`/`dayThreshold`/`dayNeed`/
  `thresholdNote`; серия — `streakBack`/`dayStreak`/`bestStreak`; цепь — `chainGrid`.
- (г) «Настройки»: `renderSettings` → `sect('groups','Блоки', groupEditor())`,
  `sect('items','Пункты', …)` (списки Минимум/Привычки, `editForm`, `addForm`,
  `goneBlock`, граница дня, зачёт дня), `exerciseEditor`, «Данные», «Система».
- (д) Разбор недели — лист `renderReview`: сетка 7×пункты (`weekGrid`, sr-only
  «отмечено n из 7»), «Три закрытые недели» (`consist`, «a · b · c из 7»),
  карточки планки.
- (е) Схема v18, `VERSION = 'minimum-v46'`, тестов 490, из них 1 ПАДАЕТ на
  исходном дереве: `З29B/6.3 (B.2.3)` зависит от дня недели (маска Пн/Ср/Пт, а
  тест не сдвигает дату; 13.09.2026 — воскресенье). Это дефект теста 29/B,
  чинится по смыслу: `await moveToWeekday(window, document, 0)` до проверки.
- Стоп-условие 2 не срабатывает: блоки — сущность хранилища (`store.groups[]`),
  хоть и связаны с пунктами по имени.

## 1. Модель данных v19 (SCHEMA_VERSION 18 → 19)

### 1.1 Блок
```
store.groups[i] = {
  name: string,          // непустое, trim, УНИКАЛЬНО среди ВСЕХ блоков, включая убранные
  caption: string,       // подпись, trim, может быть ''
  days: [{from, mask}],  // отрезки дней блока по возрастанию from; ДО первого from — все семь;
                         // [] — все семь всегда («начальный период без нижней границы»)
  removedAt: dayKey|null // убран с этого дня (включительно) либо null
}
```
- `normBlockDays(list)`: только объекты с `isDayKey(from)` и `isMask(mask)` и
  `maskDays(mask) > 0`; сортировка по from; один день — один отрезок (побеждает
  последний); подряд одинаковые маски схлопываются; ВЕДУЩИЕ отрезки с `WEEK_ALL`
  отбрасываются (до первого отрезка и так «все семь») — повторный прогон
  канонической формы её не меняет.
- `blockMaskOn(block, dayKey)`: маска последнего отрезка с `from ≤ dayKey`, иначе `WEEK_ALL`.
- `blockMaskNow(block)` = `blockMaskOn(block, todayKey())`.
- `setBlockDays(block, mask)`: пустая/невалидная маска → false. Правила
  `setSchedule` (инвариант 5): отрезок с `from = todayKey()`; хвостовые отрезки с
  `from ≥ today` снимаются (не только `=== today`: отрезок «из будущего» при сбитых
  часах иначе встал бы перед новым и нарушил порядок); если маска равна предыдущей
  (или `WEEK_ALL`, когда отрезков не осталось) — не пишется. Прежние отрезки не
  трогаются. НЕ сохраняет сам (вызывающий делает `save()`), возвращает true.
- Поиск: `findGroup(name)` ищет среди ВСЕХ (живых и убранных). `liveGroups()` =
  `store.groups.filter(live)` (у блока то же поле `removedAt`, `live` подходит).
- ЗАНЯТОСТЬ ИМЕНИ (`nameTaken(name, except)`): имя занято, если оно есть в
  `store.groups` (живой или убранный блок) ИЛИ встречается в `item.group` /
  `groupLog[].group` любого пункта, не будучи блоком `except`. Причина: блок ищется
  ПО ИМЕНИ, и переименование давнего блока в «осиротевшее» имя (оставшееся от
  импорта «(нет в списке)») задним числом применило бы его дни к прошлому чужих
  пунктов. `renameGroup` и `duplicateGroup` (подбор «(копия N)») занятые так имена
  не берут. `addGroup` в осиротевшее имя (есть в пунктах, нет в `store.groups`)
  РАЗРЕШЁН: у нового блока дни пусты или начинаются сегодня — прошлое не двигается;
  имя, которое есть в `store.groups`, — отказ.

### 1.2 Действие и привычка
- «Действие» = пункт `area 'min'`. Эффективные дни считаются ТОЛЬКО у
  `type 'daily' && area 'min'`. Привычкам (`daily habit`) дни блока НЕ
  ограничивают — их маска остаётся собственной (29/B); у параметров и недельных
  счётчиков дневных отметок нет вовсе.
- `item.schedule` у daily-min — ПЕРЕОПРЕДЕЛЕНИЕ. «Как блок» хранится маской
  `WEEK_ALL` — нейтральным элементом ∧: «отсутствие своей маски» и «свои — все
  семь» неразличимы по последствиям, поэтому второго способа сказать одно и то же
  форма данных не заводит. Существующие отрезки НЕ МЕНЯЮТСЯ ни на символ;
  `normSchedule` прежний.
- НОВОЕ поле `item.groupLog: [{from, group}]` — ИСТОРИЯ ПРИНАДЛЕЖНОСТИ блоку, только
  у `daily && area 'min'` (у прочих migrate его снимает). Зачем: пункт хранит блок
  ИМЕНЕМ, и перенос «Утро (ежедневно)» → «Школа (будни)» без истории задним числом
  выбросил бы пункт из всех прошлых выходных — ровно класс дефекта, который 28.E/A
  лечила у `active`. Пустой/отсутствующий журнал = «`item.group` на всю жизнь».
  - `groupOn(item, dayKey)`: журнал пуст → `groupNameOf(item)`; иначе группа
    последней записи с `from ≤ dayKey`; если такой нет → группа первой записи.
  - `setItemGroup(item, name)` (НЕ сохраняет; возвращает true, если имя сменилось):
    ```
    to = trim(name); was = groupNameOf(item); if (to === was) return false;
    if (item.type === 'daily' && item.area === 'min') {
      t = todayKey(); log = item.groupLog (массив, создать при нужде)
      if (!log.length && item.addedAt < t) log.push({ from: item.addedAt, group: was });
      while (log.length && log[log.length-1].from >= t) log.pop();
      prev = log.length ? log[log.length-1].group : null;
      if (prev !== to) log.push({ from: t, group: to });
      if (log.length <= 1) log.length = 0;     // одно состояние на всю жизнь — истории нет
    }
    item.group = to; return true;
    ```
  - `normGroupLog(list, item, today)` — ИДЕМПОТЕНТНА, порядок шагов обязателен:
    (1) записи-объекты с `isDayKey(from)` и строковым `group` (trim); `from <
    addedAt` → `addedAt`; сортировка по from; (2) если журнал непуст и последняя
    группа ≠ `groupNameOf(item)` → дописать `{from: max(today, последний from),
    group: item.group}` (прошлое по записям не переписывается) — ДО дедупликации;
    (3) один from — одна запись (побеждает последняя); (4) подряд одинаковые группы
    схлопываются; (5) если журнал непуст и `log[0].from > addedAt` → `log[0].from =
    addedAt`; (6) ≤ 1 записи → `[]`. Тест: `normGroupLog(normGroupLog(x)) ≡
    normGroupLog(x)` на случаях `addedAt === today`, последний from > today, пустой.
    Ограничение (в отчёт): файл, где migrate одновременно роняет битую запись и
    дописывает запись рассогласования, даёт в счёте потерь 0 — разность «было −
    стало» гасит одно другим; состояние достижимо только ручной правкой файла.
- ВСЕ места создания daily-min пункта ставят `groupLog: []` явно (каноническая форма
  без второго прогона migrate): литерал «Принять душ» шага v1→v2, `programItems`,
  копия `restoreItem` (только daily-min), `addActions`, `duplicateGroup` (daily),
  смена weekly→daily. «Поле отсутствует» каноническим не считается.

### 1.3 Эффективные дни — ОДНО правило на всё приложение
```
andMask(a, b)            // посимвольное ∧ двух масок
effectiveMaskOn(item, k):
  own = scheduleOn(item, k)
  if (!(item.type === 'daily' && item.area === 'min')) return own
  g = findGroup(groupOn(item, k))       // включая убранные блоки
  return g ? andMask(own, blockMaskOn(g, k)) : own
dueOn(item, k)  = livedOn(item, k) && effectiveMaskOn(item, k)[weekdayOf(k)] === '1'
dueNow(item, t) = live(item)      && effectiveMaskOn(item, t)[weekdayOf(t)] === '1'
weekMaskDays(item, mon) — считает дни по effectiveMaskOn (у привычек это их маска)
```
- Реализация `dueOn`/`dueNow` без аллокации строки допустима (проверка символа
  дня в own и в маске блока), но РЕЗУЛЬТАТ обязан совпадать с `effectiveMaskOn`.
- Всё прошлое по-прежнему идёт через ОДНУ точку `minDayItems` → `dueOn`; наследуют
  `minDayMarks`, `minDayClosed`, `dayScore`, `streakBack`, `dayStreak`, `bestStreak`,
  `chainGrid`, `thresholdNote`, `marksWindow`, `marksInSystem`, `missedYesterday`,
  `markYesterday`. Дневные экраны — через `dueDaily`.
- Пороги планки (`raiseEligible`/`lowerEligible`/`lowDen`) получают эффективные
  дни через `weekMaskDays` автоматически: формулы `raiseNeed/lowerNeed` НЕ меняются.
  Это не правка логики решений, а её входа: иначе действие в будничном блоке не
  набрало бы «6 из 7» никогда (ровно дефект, закрытый 29/B). В отчёт — «Решения».
- ПУСТАЯ ЭФФЕКТИВНАЯ МАСКА (own ∧ блок = 0000000) теперь достижима, а
  `raiseNeed(0) = lowerNeed(0) = 0` сделали бы пункт готовым И к повышению, И к
  понижению в одном разборе (ломает взаимоисключаемость инварианта 4). Поэтому:
  (1) guard в `raiseEligible` и `lowerEligible`: если хоть в одной неделе окна
  `weekMaskDays(item, w) === 0` → false (для m ≥ 1 поведение прежнее ни на волос);
  (2) интерфейс не даёт создать такое состояние: `updateGroup` (смена дней блока)
  отказывает, называя действия, у которых не останется ни одного дня
  (`zeroDaysIn(groupName, mask)` → имена живых daily-min пунктов блока с
  `maskDays(andMask(scheduleNow(it), mask)) === 0`); `edit-save` отказывает, если у
  действия по ИТОГОВОМУ блоку и итоговой своей маске не остаётся дней. Текст:
  «Не останется ни одного дня: {имена через «, »}» / «Нужен хотя бы один день
  недели». Форма, в которой дни не трогали, из-за нуля, пришедшего импортом, не
  отказывает — вместо этого muted-строка «Сейчас не попадает ни в один день блока».
- `clampNorm` и норма привычки — без изменений (маска привычки собственная).
- День без запланированных действий: `dayScore = null` — механизм уже есть
  (29/B), не переписывать; в цепи `.cdays i.off` — уже есть. Проверить тестами.
- Перф: пороги `bestStreak` < 50 мс, `dayStreak` < 30 мс на трёх годах — держать.

### 1.4 Операции над блоками (домен, все экспортируются в тестовый хук)
- `addGroup(name, caption = '', mask = WEEK_ALL)`: пустое имя или занятое (среди
  всех) → false. Создаёт `{name, caption: trim, days: mask === WEEK_ALL ? [] :
  [{from: today, mask}], removedAt: null}` в конец. `save()`; true. (Существующие
  вызовы `addGroup(name)` остаются корректными.)
- `updateGroup(oldName, {name, caption, mask})`: переименование через
  `renameGroup` (атомарно), подпись, `setBlockDays` при отличии маски; отказ при
  пустом/занятом имени или пустой маске — false без частичной записи; `save()`.
  (Можно реализовать внутри обработчика, но доменная функция нужна для тестов.)
- `renameGroup(old, new)`: как сейчас + переписывает `group` в `groupLog` ВСЕХ
  пунктов. Отказ, если `nameTaken(new, old)`.
- `updateGroup(oldName, {name, caption, mask})` → `{ok: true, name}` либо `{ok:
  false, reason, names?}`; reason: `'empty'` (имя пусто), `'removed'` (имя носит
  убранный блок), `'taken'` (занято), `'nodays'` (маска пуста/невалидна), `'zero'`
  (у действий `names` не останется дней). Проверки ДО записи, частичной записи нет;
  одна `save()`; отказ записи — полный откат и `{ok:false, reason:'storage'}`.
  Тексты отказа в интерфейсе: «Название не заполнено», «Блок «{имя}» убран — вернуть
  можно в «Убранных»», «Это имя уже занято», «Нужен хотя бы один день недели», «Не
  останется ни одного дня: {имена}», «Не сохранено: хранилище недоступно».
- `groupJoinRefusal(name)` → null | текст: имя принадлежит УБРАННОМУ блоку → «Блок
  «{имя}» убран — вернуть можно в «Убранных»». Вызывается в `edit-save` и
  `add-save` (привычки) ДО записи вместо того, чтобы молча привязать пункт к
  убранному блоку; `readGroupField` через «+ Новый блок…» с таким именем тоже
  отказывает (refuse, форма открыта).
- `moveGroup(name, dir)` и `reorderGroup(name, to)`: работают СРЕДИ ЖИВЫХ блоков
  (убранный соседом не считается и своё место в `store.groups` сохраняет) — ровно
  как `siblingIndexes` у пунктов. `to` — индекс среди живых.
- `removeGroup(name)`: блок жив → `removedAt = today`; ВСЕ живые пункты с
  `groupNameOf === name` (обеих областей, всех типов) получают `removedAt = today`.
  Одна запись `save()`; отказ — откат ВСЕХ полей, false.
- `restoreGroup(name)`: блок убран → запомнить `when = g.removedAt`; `removedAt =
  null`; пункты с `groupNameOf === name && removedAt === when` возвращаются по
  правилам `restoreItem` (тот же день — `removedAt = null`; позже — НОВАЯ запись
  сразу за прежней; см. инвариант 12). Для этого `restoreItem` разделить на
  несохраняющее ядро и обёртку с `save()`; поведение `restoreItem` не меняется.
  Одна запись `save()`; отказ — полный откат (массив items и поля), false.
  Ограничение (в отчёт): пункт, убранный поштучно В ТОТ ЖЕ день до ухода блока,
  вернётся вместе с блоком — отличить его нечем без нового поля; операция обратима.
- `duplicateGroup(name)` → имя копии | null: имя `«‹имя› (копия)»`, при занятости
  `«‹имя› (копия 2)»`, `(копия 3)`…; блок-копия `{name, caption: как у источника,
  days: маска источника на сегодня ≠ WEEK_ALL ? [{from: today, mask}] : [],
  removedAt: null}` встаёт СРАЗУ ЗА источником в `store.groups`; копируются ЖИВЫЕ
  пункты `area 'min'` блока (daily и weekly) в порядке `items[]`: новый id,
  `addedAt = today`, name/note/at/value/unit/type/goal, `group = копия`, daily →
  `schedule: [{from: today, mask: scheduleNow(src)}]`, `groupLog: []`, числовое
  значение → `history: [{date: today, value}]`, якоря null, `raiseAfter 0`,
  `area: 'min'`, `removedAt: null`, нечисловое → `history: []`, `formula/ladder
  null`, `ladderLog []`; `schedule` и `groupLog: []` — ТОЛЬКО у daily (тест: копия
  глубоко равна `migrate` от неё). Привычки и параметры НЕ копируются
  («действия» — пункты минимума). Копии добавляются в конец `items[]`. `save()`;
  отказ — откат.
- `deleteGroup` и «Удалить блок» УПРАЗДНЯЮТСЯ (функция, `GROUP_DELETE_WHAT`,
  `ui.groupDelete`, обработчик `group-del`, строки в `resetConfirms`/импорте).
  Причина: блок теперь несёт дни, от которых зависят прошлые числа, и по словарю
  конституции («удаляется только то, от чего не зависит ни одно прошлое число») он
  переходит из «удаляется» в «убирается». Тесты удаления переписать по смыслу на
  уход блока или снять вместе с функцией.
- `groupedItems(items)`: секции только ЖИВЫХ блоков в порядке `store.groups`;
  пункты без блока, с неизвестным или с убранным блоком — одной секцией без
  заголовка ниже всех.

### 1.5 Быстрое добавление
- `parseQuickLines(text)` → `[{name, note}]`: делить по `/\r?\n/`; каждую строку
  `trim`; пустые пропускать; разделитель — ПЕРВОЕ вхождение « · » (U+00B7 с
  пробельными символами по бокам) по регулярке на обрезанной строке
  `/^(.*?)\s+·(?:\s+(.*))?$/` → name = группа 1 (trim), note = группа 2 (trim) или
  ''; без совпадения — name = вся строка, note = ''. «/» разделителем не является;
  повторы имён не склеиваются; порядок строк сохраняется.
- `addActions(groupName, lines)` → массив созданных пунктов: для каждой строки
  daily-min пункт `{id, name, value: null, unit: '', type: 'daily', area: 'min',
  goal: null, note, group: groupName, removedAt: null, addedAt: today, at: '',
  schedule: [{from: today, mask: WEEK_ALL}], groupLog: [], raiseAfter: 0,
  raiseAfterWeek: null, lowerAfterWeek: null, history: [], formula: null,
  ladder: null, ladderLog: []}` в конец `items[]`; `groupName` может быть ''
  («Без блока»). Пустой список — `[]` без записи. Одна запись `save()`; отказ —
  откат, `[]`.

### 1.6 Migrate v18 → v19 (аддитивно, идемпотентно; days{} и reviews[] не трогать)
- Блоки: пересборка списка становится `{name, caption, days, removedAt}`:
  `caption` — строка trim (иначе ''), `days = normBlockDays(g.days)`, `removedAt =
  isDayKey ? : null`. Дубли имён по-прежнему схлопываются в первый. Старым блокам
  без полей это и есть «все дни, пустая подпись, не убран».
- Шаг v8→v9 (досборка блоков из `item.group`) обязан заводить блок в
  КАНОНИЧЕСКОЙ форме (он идёт после пересборки).
- Пункты: `daily && area 'min'` → `groupLog = normGroupLog(...)`; прочим
  `delete it.groupLog`. `schedule` — без изменений.
- Живой пункт в убранном блоке (достижимо только импортом): после нормализации
  пунктов и блоков блок, на имя которого ссылается хоть один ЖИВОЙ пункт, получает
  `removedAt = null` — иначе маска невидимого блока резала бы дни пункта, который
  интерфейс показывает «без блока». Идемпотентно.
- `programGroups()` / `seedProgram` / `defaultStore` / `emptyStore` — блоки в
  канонической форме; `programItems` для daily-min даёт `groupLog: []`; тест
  «две фабрики совпадают» держать зелёным.
- `dataCounts`: две новые категории вложенных коллекций, из которых migrate роняет
  элементы: `blockDays` (сумма `groups[].days`) — «отрезок дней блока / отрезка
  дней блока / отрезков дней блока»; `groupLog` (сумма `items[].groupLog`) —
  «запись о блоке / записи о блоке / записей о блоке». `caption`/`removedAt` —
  скаляры, категории не получают (как `note`, `at`).
- `SCHEMA_VERSION = 19`.

### 2.5 Форма правки действия (daily/weekly min)
Порядок полей: Название, Подпись, Время, [Тип], Дни, Значение+Единица, Блок,
[Цель за неделю], история планки, хвост (`removeFoot`).
- «Тип»: select `id="e-type" data-act="edit-type"` (ежедневный чекбокс / недельный
  счётчик с целью) — ТОЛЬКО если `it.addedAt === todayKey()`; иначе тихая строка
  `<p class="muted">Тип: ежедневный|недельный счётчик</p>`. Черновик — `ui.editType`.
  Смена типа в день заведения: daily→weekly снимает `schedule` и `groupLog`,
  требует цель; weekly→daily ставит `schedule: [{from: addedAt, mask: WEEK_ALL}]`,
  `goal = null`; если у недельного есть записи `weekLog` — отказ «Тип не меняется:
  по счётчику уже есть записи»; daily→weekly при сегодняшней отметке пункта — отказ
  «Тип не меняется: пункт сегодня отмечен». Прошлое не двигается: пункт существует
  только сегодня. Условие `item.addedAt === todayKey()` ПЕРЕПРОВЕРЯЕТСЯ при
  сохранении (день мог смениться при открытой форме): не выполнено — `ui.editType`
  игнорируется и сбрасывается.
- ПОРЯДОК полей уточнён: «Блок» стоит ПЕРЕД «Днями» (дни зависят от блока).
- «Дни» (только daily): блок-кандидат = `ui.groupNew ? null : (ui.groupPick ??
  it.group)`; если это ЖИВОЙ блок:
  - режим «как блок» (`ui.editOwn === false`, либо `ui.editOwn === null &&
    scheduleNow(it) === WEEK_ALL`): `<div class="field"><span>Дни</span><p
    class="dnow">как блок · {daysSummary(маска блока)}<button type="button"
    class="btn quiet" data-act="days-own">Свои дни</button></p></div>`;
  - режим «свои»: muted-строка «Дни блока: {daysSummary(маскаБлока)}» над
    `daysField(выбор, маскаБлока)`: чипы дней ВНЕ маски блока `disabled`, не «on»,
    `aria-label="{день} — не в днях блока"` (∧: вне дней блока действие не
    появится); чип «on» = `выбор[i] && маскаБлока[i]`; + кнопка
    `data-act="days-inherit"` «Как блок». `выбор = ui.editDays ??
    andMask(scheduleNow(it), маскаБлока)`. `days-own` ставит `ui.editOwn = true`,
    `ui.editDays = andMask(scheduleNow(it), маскаБлока)` («предзаполнены маской
    блока»). `days-inherit` → `ui.editOwn = false`, `ui.editDays = null`.
  - сохранение СВОЯ МАСКА ХРАНИТСЯ КАК ЕСТЬ, ∧ применяется только при чтении:
    расписание пишется ТОЛЬКО если владелец дни трогал (`ui.editDays !== null ||
    ui.editOwn !== null`); новая маска = «как блок» ? `WEEK_ALL` : `(own &
    ~маскаБлока) | (выбор & маскаБлока)` — биты вне дней блока, которые владелец
    выбрать не мог, не теряются; отличие от `scheduleNow(it)` → `setSchedule`.
    Отказ по итоговому блоку и итоговой маске, если `maskDays(andMask(новая,
    маскаИтоговогоБлока)) === 0` (см. 1.3).
  - без живого блока (''/неизвестный/«+ Новый блок…» — маска блока `WEEK_ALL`):
    обычный `daysField` своей маски, как в 29/B.
- «Блок» — существующий `groupField` (только ЖИВЫЕ блоки в вариантах, «(нет в
  списке)» для неизвестного, «+ Новый блок…»). Сохранение — `setItemGroup(item,
  readGroupField('e', item.group))` вместо присваивания (журнал принадлежности).
- `day-toggle` различает форму: открыта форма блока (`ui.groupRename !== null ||
  ui.groupAdd`) → `ui.blockDays`; иначе → `ui.editDays` (как сейчас).
- Привычка и параметр — формы прежние (привычке свои дни 29/B), `setItemGroup`

## 3. Тесты (оба уровня обязательны; фиксированные даты в домене)
Фикстура владельца (п. 6 задачи) — одна фабрика в тестах: блоки с подписями и
