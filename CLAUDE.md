# CLAUDE.md — проект «Минимум»

Персональный PWA-трекер ежедневного минимума для одного пользователя. Система различает **минимум** (неснижаемая планка, выполняется даже в худший день) и **норму** (обычный день); приложение видит только минимум. Задача — поддерживать неразрывность практики без давления: фиксировать факт и раз в неделю показывать картину. Не мотивировать, не стыдить, не развлекать.

Этот файл — конституция проекта. Он важнее любого отдельного промпта. Если задача противоречит ему — остановись и спроси архитектора, не выполняй.

## Незыблемые принципы (анти-требования)

Нарушение любого пункта = задача провалена, что бы ни просили:

- Никаких пуш-уведомлений и напоминаний.
- Никаких серий, истории и статистики прошлых дней на главном экране «Сегодня». Прошлое живёт на «Прогрессе» — отдельном экране, который открывают намеренно. Следы прошлого на «Сегодня» — только точка-маркер «вчера — пропуск» и счётчик текущей недели у недельных пунктов. Единственное точечное исключение из «никаких серий» вне «Прогресса» — серия недель привычки на «Привычках» (решение владельца от 19.07.2026, см. «Принятые ограничения»).
- Никаких красных состояний и стыдящих формулировок («провал», «пропущено», «серия потеряна») где бы то ни было. Исключений нет: строка «серия прервана» и тон --warn упразднены решением архитектора (задача 15).
- Никакой геймификации: очков, уровней, наград, конфетти, звуков, эмодзи, огня и кубков.
- Графики допустимы только на «Прогрессе» и только как тонкая линия: ступенька или спарклайн, один цвет, без осей, сетки, легенд, точек, подписей значений и тултипов; не больше одного визуала на пункт. Остальные экраны без графики. Планка дня графиком не считается — это индикатор текущего состояния, а не картина прошлого; её единственный градиент (`--accent` → `--chain`, задача 17) на это правило не распространяется.
- Никаких социальных функций.
- Никакого онбординга-туториала.
- Никакого автоматического повышения минимума: любое повышение только предлагается и требует явного подтверждения.
- Пропуск — нейтральное событие (пустая ячейка), не провал.
- Самооценка раз в неделю на разборе, не ежедневно.
- Активная лестница в приложении одна. Это правило «одно изменение за раз», выраженное механикой; формулу может нести любой пункт, лестницу — только один.
- Подсказки по заполнению живут только в форме редактирования. В списке пунктов и на дневных экранах — исключительно слова владельца; приложение не добавляет к ним ни лозунгов, ни оценок, ни цитат.
- Любой шаг прогрессии обратим: шаг назад доступен всегда и без условий. Необратимых операций в интерфейсе нет. Стирание данных — не исключение из этого правила, а его применение: чистка сохраняет прежнее состояние и остаётся отменяемой, пока владелец явно не уберёт копию вторым отдельным решением.
- `reviews[]` — архив закрытых разборов. Ни одна механика (планка вверх и вниз, серия, устойчивость привычек, готовность к новой) его не читает: все они — чистые функции от `days{}` и календаря. Единственные законные читатели — доступность следующего разбора и последнее «одно изменение». Пропуск разбора не должен блокировать ничего.

## Технические ограничения

- Ванильный стек без сборки: `index.html` + `styles.css` + `app.js` + `sw.js` + `manifest.json` + иконки. Никаких фреймворков, бандлеров и рантайм-зависимостей.
- Хостинг — GitHub Pages: только относительные пути (`./`), приложение должно работать из подкаталога.
- Основная платформа — iOS Safari standalone (iPhone 13 Pro Max): safe-area insets, `viewport-fit=cover`, высота через `100dvh`, тач-таргеты ≥44px, `font-size` полей ввода ≥16px (иначе iOS зумит при фокусе).
- PWA: cache-first через service worker, полный офлайн после первой загрузки.
- Язык интерфейса — русский.
- Темы: светлая и тёмная по `prefers-color-scheme`. Один акцентный цвет («эвкалипт»), нейтральная палитра, типографика-first.
- Вес деплоя без иконок отслеживается, но не лимитируется. Каждая
задача указывает в отчёте сырой размер, gzip -9 и прирост к
предыдущему релизу; прирост больше 5 КБ gzip за задачу объясняется
в разделе «Решения». Жёсткого потолка нет: приложение целиком
кэшируется service worker и после первой загрузки по сети не идёт,
а прежние пороги (150 → 220 → 300 КБ сырых, 80 КБ gzip) были
назначены на глаз и ни разу не отражали реальное ограничение.
Настоящий порог — время первой загрузки и парсинга на целевом
устройстве; вернуться к цифрам, когда оно станет заметным.

  Два способа экономии измерены и отвергнуты, не предлагать заново:
  деление app.js на файлы даёт +4,3 КБ gzip (задача 18) — словарь
  строится на поток, разрезанный файл теряет общие подстроки;
  сворачивание повторов шаблонов в хелперы даёт от +0,08 до +0,5 КБ
  gzip в четырёх испробованных схемах (задача 20), причём полное
  УДАЛЕНИЕ всех девяти блоков кнопок экономит лишь 336 б — это
  верхняя граница, ниже которой ни один хелпер не опустится.
  Комментарии не режем никогда: они несут обоснование решений.

  База задачи 20: 287,7 КБ сырых / 78,8 КБ gzip.

## Движение

Анимации — только тихая функциональная обратная связь на действие пользователя (задача 12). Визуальная отделка (цвета, типографика, акценты) сюда не входит — это отдельный слой.

- Только отклик на действие пользователя; ничего декоративного, самопроизвольного или зациклимого. Никаких бесконечных, пульсирующих, attention-seeking анимаций.
- Длительность перехода движения 180–260 мс (усилено в 12.1 ради читаемости; выше 260 мс нельзя — интерфейс должен оставаться отзывчивым под пальцем), кривая ease-out для появления/заполнения, ease-in для ухода. Исключение — тихое подтверждение сохранения формы: его появление и уход укладываются в это окно, а короткое удержание для читаемости (~0,8 с) переходом движения не считается.
- Ничто не движется само при загрузке экрана — единственное разрешённое исключение: лёгкий fade содержимого при показе экрана (переключение вкладок), opacity плюс короткий вертикальный подъём (`translateY` ≤ 8px → 0), не задерживающий доступность контента и не сдвигающий лэйаут/скролл (transform не вызывает reflow, без горизонтальных слайдов).
- Реализация только на CSS `transition`/`@keyframes`; без JS-анимационных библиотек. Уходу карточки разбора нужен минимальный JS-хук (`motionLeave`): класс-триггер `.leaving`, затем удаление узла перерисовкой по `transitionend` или fallback-таймауту — jsdom `transitionend` не шлёт, поэтому таймаут гарантирует и реальную очистку DOM, и независание тестов.
- Обязателен глобальный блок `@media (prefers-reduced-motion: reduce)`: все `transition` и `animation` отключаются полностью (`none !important`). Инвариант: при reduced-motion все конечные состояния (отмечено/снято, карточка ушла, экран показан, форма сохранена) достижимы мгновенно и корректны; `motionLeave` при reduced-motion удаляет узел без ожидания.

## Палитра и токены

Дизайн-токены живут в `:root` (`styles.css`); цвета переопределяются в `@media (prefers-color-scheme: dark)`, нецветовые токены общие. Работаем существующей системной гарнитурой, без новых шрифтовых семейств.

- **Нейтраль и акцент** (задачи ≤12): `--bg`/`--surface`/`--fg`, иерархия вторичного текста `--muted` → `--faint`; оба ≥4.5:1 И на `--bg`, И на `--surface` (задача 19: карточки на `--surface` появились в задаче 17, и `--faint` в тёмной теме давал на них 4,36:1); линии `--line`/`--line-strong`; `--control-border` (≥3:1) — обводка чекбокса и пустой ячейки «Цепи дней» (задача 19: `--line` давал там 1,17:1, а обводка — единственный признак дня без отметок); единственный акцент «эвкалипт» `--accent` (+ `--accent-weak`, `--on-accent`) несёт позитив/активность (отмечено, «День закрыт»/«Все отмечены», история планки, баннер, primary, фокус, текущая вкладка); `--dot` — нейтральный маркер пропуска.
- **Семантический тон** (задача 15): `--chain` — приглушённый тёплый. Назначения ровно два, третьего не заводить: линия и обводка кругов у пунктов одного блока (задача 15) и дальний край заполнения в градиенте полосы дня на «Прогрессе» (задача 17, решение архитектора). Больше нигде — в частности, в цепи дней `--chain` не используется. Не алармовый, текстом не используется. Значения (light #b06046, dark #e6a68f) подняты в задаче 16A от унаследованных от упразднённого --warn (light #9c5a44, dark #d29684); как нетекстовый элемент требует ≥3:1 к --bg — проверить тестом. Больше одного семантического тона сверх акцента не вводить без решения архитектора.
- **Тени** (задача 16.1): `--shadow-lift` (`0 6px 18px rgba(0,0,0,.16)`) — приподнятая строка при перетаскивании; `--shadow-knob` (`0 1px 2px rgba(0,0,0,.25)`) — головка тумблера. Объявлены в обеих темах; значения пока совпадают — чёрный с малой альфой читается на обоих фонах. Сырых теней в правилах нет.
- **Радиусы**: `--radius` (14px, карточки), `--radius-md` (12px, кнопки/баннер), `--radius-sm` (10px, поля).
- **Типо-шкала вторичного текста**: `--text-base` (17px), `--text-sm` (15px), `--text-xs` (13px); первичный текст — 17px body. Надписи-лейблы (`.overline`/`.h2`/`.g-label`) — единый вес 650 и трекинг .08em, различаются кеглем и цветом (muted/faint).
- **Ритм секций**: `--gap-section` (36px, заголовок секции сверху), `--gap-block` (22px).

## Архитектура

- `app.js` — один файл, порядок разделов: тексты «Системы» (`SYSTEM_TEXTS`) → хранилище и миграции → даты и граница дня → доменная логика → повышение планки → закрытие недели → экспорт/импорт → рендер → обработчики → запуск.
- Рендер — строковые шаблоны + `innerHTML`: `renderAll()`, `renderToday()`, `renderHabits()`, `renderProgress()`, `renderNotes()`, `renderSettings()` (внутри — секции `groupEditor()` и `systemSection()`), `renderReview()`, `renderDetail()`. Все пользовательские строки проходят через `esc()`. Горячие пути («Сегодня»: отметка пункта, недельный счётчик) обновляют существующие DOM-узлы точечно — CSS-переходы чекбокса и планки дня должны реально проигрываться. Полная перерисовка экрана — для структурных изменений: смена вкладки, смена логического дня, открытие/закрытие форм, добавление/удаление/перестановка пунктов.
- События — делегирование на `document` через `data-act` (click / change / input).
- Пять вкладок: Сегодня · Привычки · Прогресс · Заметки · Настройки. Разбор недели и лист детали пункта — не вкладки, а листы поверх текущей вкладки: разбор открывается баннером «Сегодня» и строкой «Прогресса», закрывается «Готово» на ту вкладку, с которой открыт. «Настройки» — сворачиваемые секции по порядку: Блоки · Пункты (списки обеих областей, граница дня и порог зачёта дня) · Упражнения · Данные (возврат стёртого, экспорт/импорт, начало отсчёта, чистка) · Система; по умолчанию раскрыты только «Пункты». Экран «Привычки» показывает сегодняшнее действие плюс полосу текущей недели и серию как тихую справку (решение владельца от 19.07.2026); остальные анти-требования действуют на нём полностью; внизу — кредо-строка «Не спеши — доверься накопительному эффекту.»
- Хранилище — `localStorage` (схема v16), неймспейс `minimum:data`, объект `store`: `items[]`, `groups[]`, `days{}`, `weekLog[]`, `reviews[]`, `pendingRaises[]`, `pendingLowers[]`, `exercises[]`, `sessions[]`, `notes[]`, `paramDecided{}`, `draftOneChange`, `weekStart`, `settings` (`dayBoundary`, `dayThreshold`, `calendarSince`, `exportedAt`, `habitSeeded`, `seed17`).
- Разбор — три решения по порядку: «Планка» (карточки повышения и понижения), «Ступень» (шаг лестницы), «Одно изменение»; сетки, счётчики, параметры и готовность к привычке живут под свёрткой «Показать неделю», по умолчанию закрытой.
- Листы поверх вкладок: разбор недели, «Тренировка» (кнопка «+» недельного счётчика) и деталь пункта. Все три закрываются таб-баром и возвращают на прежнюю вкладку с прежним скроллом.
- Тестовый хук — `module.exports` в конце `app.js`. Не удалять; при добавлении доменных функций пополнять.

## Доменные инварианты (покрываются тестами)

1. **Логический день.** Время до `settings.dayBoundary` (по умолчанию 04:00) относится к предыдущему дню: отметка в 00:30 попадает во вчера. В полночь ничего не «сгорает».
2. **Календарные недели.** Неделя — понедельник–воскресенье в логических днях (принадлежность дня неделе определяется его логическим ключом). `weekStartOf(dayKey)` — понедельник недели этого дня; `currentWeekStart()` — `weekStartOf(todayKey())`; недели существуют только с `settings.calendarSince`. Разбор предлагается только за последнюю завершённую неделю: `reviewDue()` истинно, когда `previousWeekStart = currentWeekStart − 7 дней` существует, ≥ `calendarSince` и не встречается среди `week` закрытых разборов. Окно разбора — ровно эта завершённая неделя; сегодняшний день в окно не входит. Пропуск разбора ничего не ломает: непросмотренные недели тихо проходят, их отметки остаются в `days{}` и в экспорте.
3. **Закрытие недели.** `closeWeek()` защищён guard'ом `reviewDue()` и возвращает boolean. Срез: `{closedAt, week: понедельник разобранной недели, keys — семь дней окна, perItem за них, trainings — записи weekLog той же недели, oneChange, raises, lowers, params}`; `keys` не декоративен: на него опирается шаг миграции v2→v3; после записи чистятся `pendingRaises`, `pendingLowers`, `draftOneChange` и `paramDecided`, из `weekLog` удаляются записи старше `currentWeekStart()`. Счётчик «Тренировка N из…» на «Сегодня» считает записи `weekLog` текущей календарной недели и обнуляется сменой недели, а не закрытием разбора; «отменить последний» действует только на записи текущей недели. Поле `weekStart` в старых записях `reviews` — историческое (скользящая эпоха), новые записи несут `week`. Последнее записанное «одно изменение» (`oneChange` последнего элемента `reviews`, непустое после trim) показывается тихой muted-строкой «Изменение этой недели: „…“» на экране разбора — и в ожидании, и в открытом разборе.
4. **Планка: вверх и вниз.** Обе механики считают по КАЛЕНДАРНЫМ неделям и отметкам в `days{}`; массив `reviews` в них не участвует — пропущенный разбор механику не блокирует. **Повышение** предлагается пункту type daily, active, area min, с числовой планкой > 0 и БЕЗ лестницы (два «шага вперёд» в одну неделю — два изменения за раз), когда `closedWeeks(3)` даёт три недели и в каждой `itemWeekCount ≥ 6`; «Принять» и «Не сейчас» ставят `raiseAfterWeek = currentWeekStart()`. **Понижение** предлагается пункту type daily, active, area min, СУЩЕСТВОВАВШЕМУ во всех рассматриваемых неделях (`addedAt ≤ понедельник самой ранней из `closedWeeks(2)``), когда `closedWeeks(2)` даёт две недели и в каждой `itemWeekCount ≤ 3`. Пункту, у которого нет НИ ОДНОЙ отметки в `days{}` за всё время до конца окна, понижение не адресуется: его не начинали, и облегчать нечего — планка ещё не проверялась. Повышению такая защита не нужна: его критерий требует ≥6 отметок в неделю. Шаг `lowerSuggest`: `v > 12 → round(v·0,75)`, `2 ≤ v ≤ 12 → v−1`, иначе null (кнопки шага нет, остаётся «Оставить»). «Сделать легче» пишет `recordBar` и `pendingLowers`, «Оставить» только фиксирует решение; обе ставят `lowerAfterWeek = currentWeekStart()`. Якорь сравнивается строго: предложение возвращается, когда все нужные недели позже него. Поле `raiseAfter` — историческое, в логике не используется.
5. **История планки.** `item.history` пишется общей `recordBar` из четырёх мест: принятие повышения (`acceptRaise`), принятие понижения (`acceptLower`, инвариант 4), ручная правка значения в форме и шаг порога параметра (`applyParamStep`, инвариант 10); та же функция ведёт историю нагрузки упражнений (`recordSession`, инвариант 15); повторное изменение в тот же логический день заменяет последнюю запись, а не добавляет новую. Осознанная очистка значения историю не дополняет; изменение, возвращающее значение последней записи, схлопывает её — подряд одинаковых значений в истории не бывает.
6. **Экспорт/импорт.** Экспорт → очистка localStorage → импорт восстанавливает состояние полностью. Импортируемые данные всегда проходят через `migrate()`.
7. **«Не пропускай дважды».** Точка-маркер у пункта появляется, если пункт существовал вчера (`addedAt ≤ вчера`), не был отмечен и хотя бы раз отмечался за всё время: пропустить можно только начатое, до первой отметки точки нет вовсе. По тапу точка раскрывает подпись «вчера — пропуск» и тихое действие «отметить»: единственная допустимая правка прошлого — установка отметки за вчера (только вчера, только через точку, только установка — не снятие). Глубже вчерашнего дня данные неизменяемы из интерфейса.
8. **Актуальность экрана.** Приложение хранит отрисованный логический день; при `visibilitychange`, `focus` и по таймеру, взведённому на ближайшую границу дня, сверяет его с `todayKey()` и при расхождении перерисовывает текущую вкладку. Любое дискретное действие (`onClick`, `onChange`) при расхождении не применяется — экран сначала перерисовывается (защита от записи не в тот день со stale-экрана). Непрерывный ввод (`onInput` черновика «одного изменения») guard'ом не прерывается: черновик принадлежит открытой неделе, а не дню.
9. **Зеркало данных.** Каждое успешное сохранение `store` дублируется в IndexedDB (БД `minimum`, один object store, один снапшот: JSON-строка + `savedAt` + `schemaVersion`) с дебаунсом и принудительным сбросом при уходе приложения в фон. При старте: валидный localStorage — источник истины, зеркало обновляется; пустой или битый localStorage при наличии снапшота — тихое восстановление из зеркала (битая строка по-прежнему сохраняется в corrupt-ключ до восстановления). Зеркало никогда не пишется до завершения этой стартовой проверки. Стартовое чтение (`mirrorProbe`) различает ТРИ исхода: `read` — снапшот прочитан; `empty` — база открылась, ключа нет (сюда же отсутствие IndexedDB — терять нечего); `failed` — чтение не завершилось (ошибка или таймаут `MIRROR_PROBE_MS`). При `failed` `mirrorReady` НЕ ставится: зеркало в этой сессии не пишется вовсе, потому что под недочитанным зеркалом может лежать живой снапшот, и запись дефолтного store уничтожила бы единственную страховку. Приложение при этом работает как обычно, источник истины — localStorage; строка «Данных» показывает «Резервная копия не проверена» тем же muted — это «неизвестно», а не ошибка и не тревога. Недоступность IndexedDB не меняет поведение приложения.
10. **Две области.** Каждый пункт несёт `area: 'min' | 'habit'`. Минимум — неснижаемая планка: планка дня, «День закрыт», недельный счётчик тренировок и механика повышения принадлежат только area `min`. Привычки — программа роста: ежедневные привычки (`type daily`, area `habit`; формы значения им не дают, но `value`/`unit`, пришедшие импортом, migrate сохраняет — снять их через интерфейс нечем) и недельные параметры (`type param`, только area `habit`: `pkind 'time'|'number'`, `pvalue` — минуты суток для time, число для number, `pstep` — целое со знаком, `unit` для number; `pkind` фиксируется при создании и не редактируется). У привычек своя планка дня на вкладке «Привычки». Параметры не участвуют ни в одной планке и не имеют ежедневных отметок; на вкладке — пассивная строка с текущим порогом. Порог меняется шагом только в открытом разборе: одно решение на параметр за разбор — «шаг» применяет `pstep` немедленно и пишет history, «оставить» фиксирует отказ; решения хранятся в `store.paramDecided` с привязкой к `week` разбираемой недели; решения чужой недели игнорируются, `closeWeek` переносит в срез `review.params [{id, from, to|null}]` только решения разобранной недели и очищает `paramDecided` целиком. Точка-маркер и ретро-отметка «вчера» работают для ежедневных пунктов обеих областей. Готовность к новой привычке — информационная muted-строка в разборе, когда в 2 последних ЗАВЕРШЁННЫХ КАЛЕНДАРНЫХ неделях (`closedWeeks(2)`, счёт по `days{}`) каждая активная привычка выполнила норму (≥ `normPerWeek`, инвариант 11); `reviews` не читается (см. «Незыблемые принципы»); никаких автоматических действий и кнопок.
11. **Норма и серия привычки.** Каждая привычка (`type daily`, area `habit`) несёт `normPerWeek` — целое ∈ [1..7], по умолчанию 7; только у привычек, невалидное значение приводится к ближайшему допустимому. Неделя выполнена, если отметок привычки в её календарной неделе ≥ `normPerWeek`. Серия — число подряд выполненных завершённых недель, считая назад от последней завершённой; текущая неделя не входит (сегодняшний тап серию не меняет); первый провал обрывает счёт; недели существуют только с `calendarSince`; недели до создания привычки и неполная неделя создания спецобработки не имеют — не набрав норму, они просто обрывают счёт. Серия и полоса недели — чистые функции от `days{}`, `normPerWeek` и календаря: разбор и `closeWeek` на них не влияют; смена нормы ретроактивно пересчитывает серию по всей истории. Дневные отметки привычек изменяемы через UI только за сегодня (круг) и за вчера (ретро-механизм инварианта 7); глубже и в будущее — никак.
12. **Формула и лестница.** Любой пункт type daily может нести formula — свободный текст владельца по четырём полям: {anchor, when, pair, identity, twoMin, friction, proof}; на логику не влияет, только отображается. formula несёт mode: 'build' | 'break' — режим определяет только заголовки законов, подписи полей и подсказки; ключи семи полей и их содержимое общие, смена режима текст не изменяет. Режим — свойство формулы, а не пункта. Приложение по-прежнему фиксирует только сделанное: в режиме break отметка ставится за действие-замену (поле twoMin), а не за воздержание — отсутствие события отметить нельзя. Лестница — ladder: null или {steps: [строка, …], step: индекс, steppedWeek: понедельник недели последнего шага вперёд или null, startedAt}. Лестницу может нести только один пункт: activeLadderItem() возвращает его или null. Шаг ВПЕРЁД доступен, когда step не последний, steppedWeek !== currentWeekStart() и в каждой из 2 последних ЗАВЕРШЁННЫХ календарных недель пункт набрал норму (для area habit — ≥ normPerWeek; для area min — ≥6 из 7); ставит steppedWeek. Шаг НАЗАД доступен всегда при step > 0, критериев не имеет и steppedWeek не меняет. Создание лестницы пишет в item.ladderLog стартовую запись {date, step, text, start: true}; шаги вперёд и назад пишут записи без флага start. Повторное изменение в тот же логический день заменяет последнюю запись, только если ни последняя, ни новая запись не стартовая. Снятие лестницы ladderLog не изменяет; повторное создание лестницы на том же пункте пишет новую стартовую запись. Снятие лестницы (ladder = null) не изменяет ни days{}, ни history, ни ladderLog. Автоматических шагов нет. Лестница несёт done: false. ladderSettled — вычисляемое условие: текущая ступень последняя И в каждой из 2 последних завершённых календарных недель норма выдержана. При нём владельцу предлагается закрыть привычку; done ставится только его действием и обратимо («Открыть заново»). Лестница с done: true слот не занимает — можно завести следующую, не снимая закрытую. Закрытие пишет в ladderLog запись с флагом closed и не изменяет ни days{}, ни history, ни отметки. Сообщение о том, что привычка встала, — тихая muted-строка без акцента, празднования и эмодзи: это операционный сигнал «здесь работа закончена», а не награда. Метка положения на лестнице («{step+1}/{steps.length}») допустима на дневных экранах как операционная информация — положение сейчас, а не история; она никогда не окрашивается акцентом и не влияет на сортировку пунктов. Лестницу нормализует только пункт type daily: у weekly и param `migrate` ставит `ladder = null` (иначе лестница занимала единственный слот, а снять её было нечем — лист детали открывается только для daily); `ladderLog` при этом не трогается. При нескольких лестницах в импортируемых данных migrate оставляет ту, у которой позже startedAt; при равенстве — первую по порядку items[].

13. **Блоки.** store.groups[] — упорядоченный список {name}; порядок задаёт порядок блоков на дневных экранах и в «Пунктах». item.group — имя блока; пункт с пустым или неизвестным именем рендерится без заголовка, ниже всех блоков. Блок выбирается селектом из заведённых в форме ЛЮБОГО пункта — минимума, привычки и параметра (задача 19; прежде поле было только у минимума, хотя блоки на «Привычках» работали) («— без блока», далее `store.groups` в их порядке, последним «+ Новый блок…», раскрывающий поле имени прямо в форме); свободного ввода нет — опечатка заводила блок-двойник. Имя, отсутствующее в `groups` (импорт), остаётся в списке вариантов с пометкой «(нет в списке)» и выбранным. Пустое имя нового блока его не заводит и принадлежность пункта не меняет. Блок, в котором на экране два и более активных пункта, связывает их вертикальной линией --chain, проходящей через центры кругов; линия постоянна и от отметок не зависит — она показывает принадлежность, а не результат. Обводка круга у пунктов такого блока — --chain; отмеченный круг заливается --accent. Порядок выполнения не принудителен: блокировок, предупреждений и штрафов за иной порядок нет. Переименование блока переписывает item.group у всех его пунктов атомарно; удаление очищает item.group и не удаляет ни одного пункта.

14. **Прогресс.** Единственный экран, где приложение показывает прошлое; открывают его намеренно. Всё на нём — чистые функции от `days{}`, `items[]` и календаря: разборы и `closeWeek` на них не влияют. Блоки идут по порядку: В системе · Серия · Цепь дней · Подъём · Отметки, затем строка разбора и строка выписки. Каждый блок — карточка на `--surface`; пустой блок не исчезает, а показывает одну muted-строку.

    **Два разных понятия дня, оба остаются.** «День **закрыт**» — отмечены ВСЕ активные пункты type daily, area min, существовавшие в тот день (`addedAt ≤ день`); принадлежит экрану «Сегодня» и планке дня. «День **зачтён**» — `dayScore(день) ≥ settings.dayThreshold`; принадлежит только серии и цепи дней. `dayScore(день)` — число отметок среди применимых пунктов (те же: daily, min, active, `addedAt ≤ день`), делённое на их количество; применимых пунктов нет — `null`: день пропускается в счёте и серию не обрывает. `settings.dayThreshold` — доля, по умолчанию 0,8, диапазон [0,3..1,0] шагом 0,1; настраивается степпером в «Настройках» → «Пункты» рядом с «Границей дня», подпись «День зачтён, если отмечено не меньше {N} из {M}» пересчитывается под текущее число пунктов.

    **«В системе N дней»** — число логических дней от `settings.calendarSince` до сегодня включительно (`diffDays(сегодня, calendarSince) + 1`, ноль до наступления эпохи); не прерывается никогда, отметки на неё не влияют.

    **Серия** — зачтённых дней подряд, считая назад от сегодня: сегодня, если не зачтён, ПРОПУСКАЕТСЯ (день ещё не кончился), серию не обрывает и амнистию не тратит; зачтённый день — +1; незачтённый амнистируется (не обрывает, в счёт не идёт), ТОЛЬКО если предыдущий амнистированный день отстоит больше чем на 7 календарных дней (сравнение `diffDays <= AMNESTY_GAP` — разрыв РОВНО в 7 дней уже обрывает), иначе серия обрывается; прощённый день счёт не прерывает: он идёт дальше сквозь него и упирается в следующий пропуск; два незачтённых подряд обрывают всегда (частный случай правила выше); дни до `settings.calendarSince` в счёт не входят и обрывают счёт; разборы, недели и `closeWeek` на серию не влияют. **Рекорд** (`bestStreak`) — максимальная серия за всю историю по тем же правилам; вычисляется, в `store` не хранится. Требование к нему наблюдаемое, а не предписывающее реализацию: на трёх годах истории `bestStreak` обязан укладываться в 50 мс, `dayStreak` — в 30 мс, `chainWeeks(8)` не зависит от длины эпохи (задача 23, п. 4; пороги проверяются `domain.test.js`). Как считать — дело кода; линейный проход задачи 19 даёт 1,6 мс, квадратичный возврат (streakBack от каждого дня) — 717 мс и замораживал «Прогресс». Подпись в интерфейсе обязана совпадать с правилом: «Пропуск прощается, если прошлый был больше недели назад».

    **Цепь дней** — сетка последних 8 календарных недель по фактам `days{}`; ячейка: `dayScore ≥ порога` — сплошная заливка `--accent`, `0 < dayScore < порога` — контур `--accent` без заливки, `dayScore = 0` — пустая ячейка с обводкой `--control-border` (≥3:1: обводка здесь несёт информацию, а не разделяет); будущие дни текущей недели и дни до `calendarSince` не рисуются. Не осталось НИ ОДНОЙ видимой ячейки (все восемь недель до `calendarSince` либо впереди) — сетка не рисуется вовсе, блок показывает одну muted-строку «Цепь начнётся с первого дня отсчёта.»; sr-only при этом не объявляет недели, целиком лежащие до `calendarSince`, — несуществующей недели «зачтено 0 из 7» не бывает. `--chain` в блоке цепи не используется: тёплый тон закреплён за связкой блока, сетка дней — про выполнение. **Подъём** — по одному визуалу на пункт, у которого ≥2 записей в `history` (первична) либо ≥2 в `ladderLog`. **Отметки** — число отметок пункта в окне `calendarSince…сегодня`; знаменатель — число дней от ПОЗДНЕЙШЕЙ из двух дат (`item.addedAt` и `settings.calendarSince`) до сегодня включительно, а не общее число дней в системе. Пока ни у одного пункта нет ни одной отметки в окне, блок показывает одну muted-строку «Первые отметки появятся здесь.» вместо ряда «{имя} · 0 из N»: ряд нулей — не картина, а её отсутствие. Пунктов нет вовсе — прежняя строка «Пунктов пока нет.».

15. **Упражнения и тренировки.** `store.exercises[]` — упорядоченный список `{id, name, unit, value, history[], active, addedAt}`: `value` — текущая рабочая нагрузка, `history` пишется общей `recordBar` по правилам инварианта 5. `store.sessions[]` — `{id, date, entries: [{exId, value}], note}`. Кнопка «+» недельного счётчика на «Сегодня» открывает лист «Тренировка», а не инкрементирует счёт: «Записать» создаёт сессию за `todayKey()`, обновляет `value` каждого упражнения на введённое (историю пишет только при изменении) и инкрементирует `weekLog`; «Отмена» не пишет ничего. Пустое или невалидное поле в сессию не идёт и нагрузку не трогает. Активные упражнения ЕСТЬ, но ни одно не заполнено валидным значением — «Записать» не пишет ничего вовсе: ни сессии, ни `weekLog`; лист остаётся открыт, поля не переписываются, и раскрывается тихая muted-строка «Нечего записать…». Активных упражнений нет вовсе — поведение прежнее: сессия с пустым `entries` и `weekLog` +1, потому что заполнять нечего и это единственный способ засчитать тренировку. Шаг «−» не доводит поле до значения, которое сессия отбросит: результат ≤ 0 поле не меняет. «Отменить последний» снимает запись `weekLog` и сессию того же дня; значения упражнений при этом не откатываются. Упражнения заводятся, переименовываются, получают единицу, порядок и выключение в «Настройках»; удаления нет — как и у пунктов. Упражнение с ≥2 записями истории попадает в «Подъём» на «Прогрессе» по общим правилам инварианта 14.

16. **Заметки и выписки.** `store.notes[]` — `{id, date, text, kind, source, updatedAt}`: `date` — логический день записи, `updatedAt` — время последней правки, `kind` — `'note' | 'quote'` (по умолчанию `'note'`), `source` — строка, непустой только у выписки (у заметки миграция обнуляет). Вид задаётся при создании и не редактируется. Экран «Заметки»: сверху две кнопки — «Новая заметка» и «Новая выписка» (форма выписки отличается только полем «Источник», необязательным), ниже общий список обоих видов от новых к старым (по `date`, при равенстве по `updatedAt`); тап по карточке раскрывает правку. У выписки текст показывается в кавычках, источник — muted-строкой. Пустой текст при сохранении удаляет запись; явная «Удалить» подтверждается вторым тапом. Текст хранится с trim, пустых записей не существует — миграция такие отбрасывает. Черновик формы живёт в своём слоте (`noteDraft`) и переживает перерисовку, включая смену логического дня. На «Прогрессе» последней строкой показывается одна выписка, выбранная детерминированно по номеру логического дня (`daysInSystem() mod количество выписок`), а не случайно; выписок нет — строки нет. Ни поиска, ни тегов, ни вложений, ни форматирования, ни связей с пунктами.

17. **Порядок и перетаскивание.** Пункт двигается только среди соседей по блоку своей области — и стрелками (`moveItem`, `canMoveItem`), и перетаскиванием (`reorderItem`); границы движения — первый и последний пункт блока, пункты чужих блоков остаются на своих позициях в `items[]`. Блок пункт меняет полем «Блок» в форме правки: порядок и принадлежность — разные решения. Перетаскиваются пункты внутри блока, блоки между собой (`reorderGroup`) и упражнения (`reorderExercise`). Захват — долгим нажатием 250 мс на Pointer Events без библиотек; движение до захвата считается скроллом и захват отменяет, но не любое, а сдвиг больше `DRAG_SLOP` = 8px — иначе дрожание пальца срывало бы захват; отмена — Escape или уход пальца за пределы списка вбок; отпускание пишет порядок и сохраняет. Стрелки ↑↓ остаются всегда — это доступный путь, а не дубль.

18. **Чистка и её отмена.** «Начать с чистого листа» живёт внизу секции «Данные» и требует двух тапов; перед ним — список стираемого числами и кнопка «Сначала скачать копию». Стирание кладёт прежний `store` целиком в ключ `minimum:data:wiped` (`{store, wipedAt, stats}`) и заменяет текущий пустым: ни одного стартового пункта, `calendarSince = nextCalendarMonday(сегодня)`. Переживают чистку ровно две настройки — `settings.dayBoundary` и `settings.dayThreshold`: обе описывают, как приложение считает день, а не данные владельца. Копию некуда положить — чистка не выполняется вовсе. Зеркало IndexedDB сбрасывается немедленно (`flushMirror`), иначе следующий старт при пропавшем localStorage восстановил бы стёртое из старого снапшота. Пока копия существует, «Данные» первой строкой показывают «Стёрто {дата} · N пунктов, M дней отметок» с кнопками «Вернуть» (проводит копию через `migrate` и убирает ключ) и «Убрать копию» (вторым тапом). Копия хранится одна, последняя, и в экспорт/импорт не входит: экспорт отдаёт текущий `store`, импорт ключа не касается. После чистки `calendarSince` лежит в будущем — все экраны обязаны работать в этой пустой эпохе, `currentWeekStart()` при этом null. Пустой store, оставленный чисткой, несёт `settings.seed17 = true`: иначе следующий старт прогнал бы его через `migrate` и посев (инвариант 19) вернул бы стёртое.

19. **Посев программы.** `migrate()` заводит стартовую программу владельца — три блока (Утро · Подряд · Движение), девять пунктов и пять выписок — только когда `items[]` ПУСТ, не стоит `settings.seed17` и данные НЕ пришли извне; после посева ставит флаг. Стартовая программа принадлежит первому запуску, а не всякому пустому store: `migrate(s, {external: true})` (импорт файла и возврат стёртой копии) посев не запускает независимо от `schemaVersion` и наличия флагов, а пустому внешнему store сразу проставляет `seed17` и `habitSeeded`, чтобы следующий старт не засеял его уже как «первый запуск». Без этого файл, снятый версией до задачи 17 сразу после чистки, приносил пустой `items[]` и получал девять чужих пунктов. На непустых данных не делает ничего и флага не ставит, поэтому повторный прогон `migrate` ничего не дублирует. Числовым пунктам заводится стартовая запись `history` (правило `defaultStore`). Из старых шагов засеянному store опасен ровно один — v1→v2: он переписал бы блоки по именам прежнего набора («Тренировка» → «Тело»), поэтому закрыт флагом `seeded`. Остальные шаги ему адресованы, но безвредны (пустые reviews/ladder/groups уже в канонической форме), а v3→v4 даже нужен: `seedProgram` не выставляет `settings.exportedAt`. Посев привычек шага v4→v5 отключается не этим флагом, а `habitSeeded = true`. Всё заведённое живёт как обычные записи — правится, выключается, выписки удаляются. `defaultStore()` (первый запуск без данных и без зеркала) через `migrate` не проходит, поэтому собирает тот же набор сам: состав живёт в одной фабрике (`programItems` / `programQuotes` / `programGroups`), два набора разойтись не могут — это покрыто тестом.

## Правила изменений

- Изменил структуру `store` → подними `SCHEMA_VERSION` и добавь шаг в `migrate()`. Данные пользователя не теряются никогда, миграции идемпотентны.
- Изменил любой файл деплоя → подними `VERSION` в `sw.js`, иначе cache-first отдаст старую версию.
- Добавил доменную функцию → экспортируй в тестовый хук и напиши тесты доменного уровня.
- Функция рендера с ВЕТВЛЕНИЕМ (не подстановка строки, а выбор между состояниями) получает тест на каждую ветку. Проверенной одной ветки достаточно не бывает: полоса дня «Прогресса» держалась на закрытом дне, где числитель равен знаменателю, и подмена одного другим проходила молча.
- Перед завершением задачи: `npm test` зелёный, анти-требования не нарушены, вес указан в отчёте.
- Не делай ничего сверх поставленной задачи. Идеи и найденные проблемы — в отчёт, не в код.
- Мутационные проверки и любые деструктивные git-операции (`checkout --`, `reset --hard`, переписывание истории) — только в изолированной копии рабочей директории, никогда в живом дереве.
- Раздел «Сделано» отчёта ведётся строго по номерам пунктов исходного промпта; каждый пункт получает явный вердикт: сделан / не сделан / отменён решением архитектора.
- Принятые ограничения: `dateKeyShift` вычитает фиксированные четыре реальных часа, поэтому в дни перевода стрелок граница логического дня смещается на час. Регион владельца — America/Toronto: 1 ноября 2026 день сменится в 03:00 местного, 14 марта 2027 — в 05:00. Окно попадает в сон, практический риск нулевой; ограничение осознанное и датированное, не «регион неактуален». Зеркало IndexedDB — страховка от исчезновения localStorage, а не запасное хранилище при отказе записи: localStorage — единственный источник истины, при его недоступности отметки текущей сессии не сохраняются (пользователь видит баннер). Обновление приложения тихое: новая версия применяется при следующем запуске, открытая страница не перезагружается. Manifest несёт тёмные цвета бренда; цвета для каждой темы iOS берёт из двух meta theme-color с media в index.html. Таб-бар — навигация (nav + aria-current), не ARIA-tabs. Гарантированный анонс статусов скринридером — только у планки дня (постоянный узел + точечное обновление); остальные status-узлы рождаются вместе с текстом, их анонс нестабилен — осознанно. Иконки — закоммиченные артефакты: при смене палитры или мотива перегенерировать вручную (`node tools/make-icons.mjs`). Ретро-отметка, сделанная в день закрытия недели, ложится в `days{}` (и в экспорт), но в уже замороженный срез `reviews` не попадает: срезы неизменяемы, первичен факт. Переход со скользящих недель: `calendarSince` ставится миграцией в понедельник дня миграции (если это понедельник) или ближайший следующий; до этой даты разбор недоступен, счётчик тренировок доживает от прежнего `store.weekStart`. Последняя скользящая неделя и дни до `calendarSince` среза не получают — их отметки остаются в `days{}` (расширение принципа «срезы неизменяемы, первичен факт»). Решение владельца от 19.07.2026: серия недель привычки — точечное исключение из «никаких серий», тихая ретроспективная справка muted-текстом на «Привычках» и в разборе — операционная информация программы роста, по аналогии с недельным счётчиком; запрещёнными остаются празднования, эмодзи, цветовое давление, сортировка по серии, призывы «не прервать» и любые уведомления. Миграция v6 аддитивна: `days{}` и `reviews[]` не изменяются. Конфликт двух лестниц, начатых в один логический день, разрешается порядком в items[] — правило произвольное, но пользователь один и слияния экспортов не предполагается. Отмена последней тренировки («отменить последний») снимает запись `weekLog` и сессию того же дня, но НЕ откатывает рабочие нагрузки упражнений: история планки фиксирует, что нагрузка была изменена, и переписывать её задним числом нельзя (решение задачи 16D). Начало отсчёта задаётся владельцем свободно, включая будущую дату (задача 22): поле «Начало отсчёта» потолка не имеет, значение нормализуется к понедельнику своей недели. Пустая эпоха — законное состояние приложения, а не только следствие чистки: при `calendarSince` впереди `currentWeekStart()` равен null, разбор недоступен, серия и цепь пусты, все экраны обязаны работать. Вход в лист детали с экрана «Пункты» ведёт из формы правки, а не из строки списка: кнопка в строке сужала текстовую колонку со 181 до 137px и переносила длинные названия (решение архитектора от 13.08.2026, отмена п. 3.1 задачи 14.1).

## Тесты

- Каталог `tests/`, раннер `node --test`.
- Два уровня, оба обязательные. **Доменный** — `tests/domain.test.js` и `tests/regression.test.js`: без jsdom, через тестовый хук, доли секунды на файл; любая доменная функция обязана иметь тест этого уровня. **Интерфейсный** — `tests/dom.test.js` в jsdom: любая функция рендера обязана иметь тест этого уровня. Дымовым он больше не называется: он держит разметку, точечные пути и поведение экранов, а не только «отрисовалось без исключений». `app.js` в jsdom загружать через `vm` в контексте window — ветка `module.exports` перехватывает обычный `require`.
- Точечное обновление DOM обязано давать то же, что полная перерисовка на тех же данных: сторож общего вида в `dom.test.js` сравнивает разметку экрана после горячего пути с перерисованной. Известные расхождения изымаются из сравнения только вместе с отдельным тестом, который их закрепляет.
- Контраст проверяется обходом ВСЕЙ палитры `:root` в обеих темах: каждый токен отнесён к корзине — текст (≥4,5:1), нетекст (≥3:1), фон или служебный (порога нет). Токен, которого в корзинах нет, роняет тест: добавить цвет, не приняв решения о контрасте, нельзя.
- Константы времени (`MIRROR_PROBE_MS`, `MOTION_MS`, `FLASH_MS`, `DRAG_HOLD` и прочие) объявляются через `timing()` и подменяются тестом до загрузки `app.js` объектом `globalThis.MINIMUM_TIMING`. Рантайм приложения от этого не меняется: значения по умолчанию живут в `TIMING_DEFAULTS` и проверяются отдельным тестом домена, который подмен не видит. Тест, чей предмет — сама величина константы, обязан проверять её явно, а не полагаться на подобранную паузу.
- `devDependencies` допустимы только для тестов (jsdom, fake-indexeddb). Рантайм приложения — без зависимостей.
- Замок версии: `tests/releases.json` хранит отпечаток (sha256) файлов деплоя каждого выпущенного релиза. Изменил файл деплоя, а `VERSION` в `sw.js` не поднял — `sw.test.js` падает. Подняв версию, отпечаток записывают в релизном коммите: `node tools/release-lock.mjs`. Три правила замка: `VERSION` — СЛЕДУЮЩИЙ ПО СЧЁТУ относительно максимума в `releases.json` (ни прыжка вперёд, ни имени вне последовательности; номер сравнивается числом, не строкой); набор релизов ТОЛЬКО РАСТЁТ — версии предыдущего коммита обязаны остаться в текущем (сверка через `git show HEAD:tests/releases.json`; git недоступен — пропуск с `console.warn`, но не молча); алгоритм отпечатка живёт в ОДНОМ модуле `tools/deploy-hash.mjs`, который читают и тест, и инструмент. `release-lock.mjs` отказывается переписывать хеш уже выпущенной версии и выходит с кодом 1.
- Сторож разметки: `tests/markup.snapshot.json` хранит outerHTML всех форм, тест сверяет побайтово. Сам он не восстанавливается: снимка нет — падение с инструкцией, а не тихая запись (иначе удалённый файл разоружал бы проверку молча). Запись только по явной переменной: `MARKUP_SNAPSHOT=write node --test tests/dom.test.js` — после осознанной правки вёрстки форм.
- Запуск: `npm test`.
